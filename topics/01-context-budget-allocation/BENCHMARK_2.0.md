# Benchmark 2.0 — Real-API Context-Budget Allocation

Benchmark 2.0 tests the repository's four deterministic context-allocation
strategies with frozen public data, OpenAI-backed retrieval, real model
inference, and read-only tools. It is the real-data successor to the synthetic
Benchmark 1 experiment described in [BENCHMARK_GUIDE.md](BENCHMARK_GUIDE.md).

The completed reference run used `gpt-5.6-luna`, executed all 224 planned
cells, recorded no API or execution failures, and cost approximately **$2.91**
in total API usage.

This is a research benchmark, not a production allocator or a validation of
confidential tenant isolation.

---

## Executive summary

Benchmark 1 answered: *Do these allocators satisfy deterministic safety and
budget invariants on inspectable synthetic workloads?*

Benchmark 2.0 asks the harder follow-up: *When the candidate context comes from
real sources and the selected evidence is consumed by a real model, which
allocator produces the best grounded answers for the cost?*

The reference run found:

- `utility` and `waterfill` tied for the strongest answer and evidence metrics.
- `utility` was marginally cheaper than `waterfill`.
- `fixed_quota` remained competitive but used more tokens and cost more.
- `recency` performed substantially worse under evidence pressure; recent
  context was often not the context containing the required fact.
- Every allocator retained all protected and must-survive items.
- No unauthorized source item reached a model prompt.
- All 224 scheduled cells completed without an API or execution error.

The current evidence therefore supports **utility as the leading candidate for
the next evaluation**, not as a universal or production-ready winner. The
dataset is intentionally small, public, and reproducible.

The design separates **data acquisition** from **model evaluation**. Live
source data and RAG results are captured once and frozen. Every allocator then
sees the same candidate bytes, eliminating source drift as an explanation for
differences between allocator results.

## What is real, and what is frozen

### Real operations

The benchmark performs genuine external operations:

- GitHub and PyPI data is fetched from their public APIs.
- Retrieval chunks and queries are embedded with
  `text-embedding-3-small`.
- Answers are generated by the configured OpenAI model.
- Tool-mode requests expose real tool schemas.
- Accepted tool calls are validated and resolved through the real read-only
  tool layer; their underlying API results are captured live once.
- Token usage and estimated dollar cost are recorded from the API workflow.

### Frozen operations

Reproducibility requires that some live results be captured once and replayed:

- Public source responses are stored with provenance and content hashes.
- RAG results are frozen after real OpenAI retrieval.
- Identical read-only tool requests are captured once and replayed byte for
  byte across allocator cells.

This is deliberate experimental control, not simulation. If four allocators
received four independently fetched versions of a GitHub response, the result
would confound allocator quality with network timing and source drift.

Benchmark 2.0 extends the original experiment rather than replacing it.

- the `ContextItem` data model;

This reuse matters because it changes only the parts under investigation: real
retrieval, real source material, real inference, and real tool behavior.

## Phase 1: capture real source material

The capture phase performs five jobs:

1. Fetch allowed public sources over HTTPS.
2. Attach source provenance and access scope.
3. Normalize and redact persisted content.
4. Run real OpenAI-backed retrieval.
5. Hash and atomically write the immutable capture.

The reference capture contains:

- **112** real source artifacts;
- **6** embedding retrieval queries;
- **61,637** embedding tokens;
- **$0.00123274** recorded RAG cost;
- no persistent OpenAI vector-store resources.

### Embedding RAG

The founder-owned key used for the reference run could create embeddings but
did not have `vector_store.write`. Benchmark 2.0 therefore supports an
equivalent permission-compatible retrieval path:

1. deterministically chunk the real documents;
2. embed all chunks with `text-embedding-3-small`;
3. embed each benchmark query with the same model;
4. compute cosine similarity locally;
5. rank with deterministic tie-breaking;
6. persist retrieved chunk IDs, scores, provenance, and hashes.

The semantic representation is still produced by the real OpenAI embeddings
API. Only storage and cosine ranking are local. A vector-store backend remains
available when the key has the necessary permissions.

## Phase 2: construct workloads

The workload builder verifies the capture hash before constructing any model
request. It then converts captured material into `ContextItem` candidates.

Each candidate carries enough metadata to make allocation auditable:

- stable item ID;
- context class;
- source and immutable provenance;
- access scope;
- token count;
- sequence or retrieval rank;
- relevance where applicable;
- protected and truncatable flags.

Each workload also has a separate `GroundTruth` object containing the expected
answer, required evidence IDs, required sources, and any expected tool call.
Ground truth is used by the grader; it is not exposed to the allocator as an
answer hint.

### Protected and elastic lanes

Protected items contain information that must survive allocation, such as
system/security rules, the active user request, and required tool schemas.
Elastic items—history, retrieval, tool results, agent messages, and memory—may
compete for the remaining budget.

All candidates first pass through scope filtering. An unauthorized item is
dropped before allocation, not merely assigned a low score.

---

## Phase 3: allocate and assemble context

Every cell applies one allocator to the same versioned candidate set:

- `fixed_quota` assigns predefined class shares, then spills unused capacity.
- `waterfill` assigns class floors and distributes remaining capacity by
  weight, subject to class ceilings.
- `utility` prioritizes item-level value under the available token budget.
- `recency` prioritizes the newest eligible elastic items.

Protected items are handled first. Elastic allocation only begins when the
protected lane is valid. The selected items are then assembled in a stable
order, and hashes identify both the input candidates and the final selection.

The allocator operates only on the input budget. Output and tool-call reserves
are removed from the physical context window before allocation begins.

---

## Phase 4: real model and tool execution

The runner submits the deterministically assembled prompt to the OpenAI
Responses API. In tool mode it may receive a structured tool call, validate the
tool name and arguments, resolve it through the read-only tool executor, append
the result, and request the final answer. During the allocator matrix, the
executor replays the bytes captured for the same canonical tool request instead
of issuing a different live public-API request for each cell.

The tool layer enforces:

- a fixed allowlist of read-only operations;
- argument validation;
- HTTPS and host restrictions;
- bounded response sizes and timeouts;
- duplicate-call detection;
- redaction before persistence.

The tool executor does not provide arbitrary shell, filesystem, or network
access to the model.

## Evaluation matrix

The reference run contains exactly 224 cells:

```text
16 workloads × 3 standard profiles × 4 allocators = 192
 4 workloads × 1 additional 256k profile × 4       =  16
 4 workloads × 1 tool-mode 64k profile × 4         =  16
                                                     -----
                                                       224
```

The standard profiles are 32k, 64k, and 128k. Four selected workloads also
exercise 256k context, and four exercise explicit tool mode at 64k.

Each cell has a stable identity derived from its workload, allocator, profile,
mode, and frozen inputs. Completed cells are appended to a resumable ledger,
so an interrupted run does not pay to repeat successful work.

## What the grader measures

The grader is deterministic; one language model does not judge another.

It records:

- exact-answer correctness;
- required-source recall;
- citation validity;
- selected evidence recall;
- protected and must-survive retention;
- unauthorized-context leakage;
- budget overflow and tokenizer mismatch;
- tool choice, arguments, execution status, and duplication;
- input/output tokens and estimated cost.

`overflow` and `mismatch_overflow` are intentionally different. An `overflow`
workload has more eligible candidate material than its input budget and is the
condition the allocator is designed to handle. `mismatch_overflow` means the
assembled request unexpectedly exceeded the intended budget and indicates a
token-accounting defect.

The reference run had 89 expected workload-overflow rows and **zero** mismatch
overflows.

### Tool-mode interpretation

There were 16 tool-mode cells. Twelve produced the expected tool call; all 12
selected the correct tool, supplied correct arguments, executed successfully,
and avoided duplicate execution. Four `mixed_overflow` cells answered correctly
from evidence already present in the selected context instead of calling the
tool.

That distinction is visible in the results: it is model tool-use compliance,
not an API or executor failure.

### Cost

- Worst-case preflight estimate: **$3.842048**
- Configured client limit: **$4.50**
- Fixed scheduler buffer: **$0.50**
- New-call scheduling boundary: **$4.00**
- Recorded model cost: **$2.90916860**
- Recorded RAG cost: **$0.00123274**
- Recorded total API cost: **$2.91040134**

The dollar limit is a client-side safety mechanism, not a provider-enforced
billing ceiling. Only provider or project controls can guarantee a hard spend
limit. Pricing and model availability must be rechecked before another paid
run.

## Interpretation

The result rejects a tempting but unsafe simplification: filling the context
window with the newest available material is not the same as preserving the
most useful evidence. `recency` cost roughly as much as `fixed_quota` while
producing much lower answer and evidence scores.

`utility` and `waterfill` selected effectively the same evidence on this
corpus. Their small cost difference is not enough to establish a universal
winner, but `utility` is the best candidate for the next round because it tied
the strongest quality metrics at the lowest observed mean cost.

The next evaluation should test whether that conclusion survives:

- more diverse repositories and package ecosystems;
- longer conversational and tool traces;
- production-like authorization metadata;
- noisy or contradictory retrieval;
- multiple models and serving tokenizers;
- repeated runs to measure model-output variance;
- private data in an approved, isolated environment.

## Safety and credential handling

Secrets are accepted only through environment variables. Do not place API keys
in `.env.example`, source files, shell history committed to the repository, or
generated result artifacts.

The implementation also uses:

- HTTPS host allowlists for public APIs;
- output-size and timeout limits;
- credential-pattern redaction;
- atomic artifact writes;
- capture and candidate hashes;
- explicit `--live` consent for paid/networked paths;
- separate preflight caps for RAG and model inference;
- explicit cleanup for persistent vector-store resources.

Embedding capture creates no persistent OpenAI vector resources. Vector-store
capture does, so cleanup requires a separate explicit command and the exact
vector-store ID.

## Reproducing the benchmark

Run commands from `topics/01-context-budget-allocation`.

### 1. Install dependencies

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Export credentials in the shell that runs the commands

```bash
export OPENAI_API_KEY="..."
export GITHUB_TOKEN="..."  # optional, recommended for GitHub rate limits
```

Never paste the value into a tracked file. A variable exported in one terminal
is not automatically inherited by an unrelated terminal that was already
open.

### 3. Capture real data and embedding RAG

```bash
python -m benchmark.real.capture \
  --live \
  --rag-provider embeddings \
  --max-rag-cost-usd 0.10
```

Capture refuses to overwrite an existing frozen capture unless `--force` is
supplied. Replacing a capture creates a different experiment and incurs new API
usage.

### 4. Run or resume the matrix

```bash
python -m benchmark.real.run \
  --live \
  --model gpt-5.6-luna \
  --max-cost-usd 4.5 \
  --resume
```

Always inspect the printed preflight estimate before allowing the run to
continue. Use the model and budget approved for that specific run; the command
above documents the reference configuration, not a permanent pricing promise.

### 5. Generate reports

```bash
python -m benchmark.real.report
```

Generated captures and paid-run results are intentionally Git-ignored. The
reporter writes the detailed JSON, CSV, and Markdown artifacts under
`results/real/`.

### 6. Clean up a vector-store run, if one was used

```bash
python -m benchmark.real.cleanup --live --vector-store-id vs_...
```

Do not guess the ID. Embedding-mode runs do not require this step.

## Validation before changing or publishing the benchmark

From the topic directory:

```bash
python -m pytest
ruff check benchmark
ruff format --check benchmark
python -m compileall -q benchmark
```

Before committing, also verify that generated captures/results remain ignored
and scan the staged diff for credentials. A passing unit suite does not prove
that a live model run occurred; live-run claims must be backed by the generated
ledger and report.

## Limitations

- The corpus contains public technical data, not confidential production data.
- `cross_tenant` tests source-scope filtering and must not be presented as proof
  of production tenant isolation.
- Retrieval quality depends on a small frozen corpus and fixed queries.
- The model can answer from selected context instead of obeying an expected
  tool-call preference.
- Exact grading is reliable for the bounded factual tasks used here, but does
  not measure every aspect of answer usefulness.
- Client-side cost guards reduce risk but cannot guarantee the provider bill.
- One completed run cannot quantify inference variance across repeated runs.

---

## Bottom line

Benchmark 2.0 demonstrates that the allocator comparison survives contact with
real source acquisition, real retrieval, real inference, tool execution, and
measured API cost. It also changes the conclusion from the synthetic first
pass: under these real-data workloads, item-level utility and weighted
water-filling preserve substantially more useful evidence than pure recency.

The evidence supports taking `utility` forward into a broader Benchmark 3,
while retaining authorization filtering, the protected lane, deterministic
assembly, replay hashes, and cost preflights as non-negotiable architecture.
